# 🌍 Internationalization

Structure for many locales from day one, even if you launch with one. Retrofitting i18n later means touching every string in the app.

## A tiny, dependency-free translator
You rarely need a heavy i18n library. A flat key catalog + interpolation covers most apps:
```ts
export function createTranslator(catalog: Record<string, string>) {
  const t = (key: string, vars?: Record<string, string | number>) => {
    const tmpl = catalog[key];
    if (tmpl === undefined) return `⟦${key}⟧`;   // loud miss — never a silent fallback
    return vars ? interpolate(tmpl, vars) : tmpl;
  };
  t.has = (key: string) => Object.hasOwn(catalog, key);
  return t;
}
```
- **Missing keys render loudly** (`⟦some.key⟧`) so gaps are obvious in dev, not invisible in prod.
- Put it in a shared `packages/i18n` so web and mobile share the same catalog and locale rules.

## Catalog: nested authoring, flat lookup
Author by feature namespace, flatten to dot-keys at build/load:
```json
{
  "nav": { "home": "Home", "billing": "Billing" },
  "approvals": {
    "empty": "Nothing waiting on you.",
    "pending": "{count} pending approval",
    "pending_plural": "{count} pending approvals"
  }
}
```
→ `nav.home`, `approvals.pending`, `approvals.pending_plural`. Interpolate with `{var}` placeholders; pick the `_plural` key by count.

## Locale resolution
- Supported set + a default: `["en","es","pt","fr","de"]`, default `en`.
- **Normalize tags:** strip region (`pt-BR` → `pt`), lowercase, fall back to default.
```ts
export function normalizeLocale(tag?: string, supported = SUPPORTED, def = "en") {
  if (!tag) return def;
  const primary = tag.split("-")[0].toLowerCase();
  return supported.includes(primary) ? primary : def;
}
```
- **Mobile** passes locale per request (`?locale=es`); the same normalization runs client-side ([mobile](../stack/mobile.md)).

## SRP for i18n
i18n is itself a set of single-responsibility modules — don't cram it into one file ([SOLID/SRP](../architecture/solid-srp.md)):
```
packages/i18n/src/
├── translator.ts   # createTranslator() — lookup + interpolation only
├── catalog.ts      # nested → flat catalog flattening
├── locales.ts      # supported set, default, normalizeLocale()
├── interpolate.ts  # {var} substitution + pluralization
└── index.ts        # public exports
```
- **The translator doesn't know about locale resolution; the resolver doesn't know about interpolation.** One reason to change each.
- Catalog files (`en.json`, `es.json`, …) are data, not code — keep them out of the logic modules.
- This is what lets web and mobile share `translator`/`locales` while supplying their own catalogs.

## Rules
- **No hardcoded user-facing strings** — every one goes through `t()`.
- **One catalog per locale**, namespaced by feature; keep keys stable.
- **Dates, numbers, money are NOT i18n strings** — format them with `Intl` per locale → [dates-money-timezones.md](dates-money-timezones.md).
- Keep the shared locale set identical across web + mobile so translations are written once.
- **SRP:** translator / catalog / locale-resolution / interpolation are separate modules.
